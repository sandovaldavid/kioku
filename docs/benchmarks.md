# Performance benchmarks

Machine-readable and human-readable results for the metrics issue #257 asks for: cold-start
time, indexing time/memory by vault size, search latency (p50/p95) by mode, update-to-queryable
latency, embedding cache size/reuse, schema-token cost by capability profile, and retrieval
quality (Recall@K/MRR/NDCG@K).

The runner lives at [`scripts/Kioku.Benchmarks`](../scripts/Kioku.Benchmarks) (a `suite`
subcommand alongside the project's existing BenchmarkDotNet micro-benchmarks). The full JSON
report from the run summarized below is committed at
[`scripts/Kioku.Benchmarks/output/benchmark-report.json`](../scripts/Kioku.Benchmarks/output/benchmark-report.json).

## Read this before trusting a number

This ran once, on a single development machine, in a single session — **not** a controlled or
isolated benchmark environment. Other local processes (including other Ollama models loaded on
the same box) could share CPU/IO with the run. Treat every number below as one data point
illustrating orders of magnitude and relative behavior (e.g. "cache reuse is ~150x faster",
"semantic search is ~15-20x keyword"), not a guaranteed SLA or a cross-machine comparison
baseline. Re-run on your own hardware with the reproduce commands below before relying on
absolute figures.

## Dataset

- **Indexing time / memory by size**: synthetic vaults generated by
  `SyntheticVaultGenerator` (varied paragraph count, tag count, and a fraction of notes
  wikilinking each other) at **100, 500, 1,000, 2,000, 10,000, and 50,000 notes** — all sizes
  above were run to completion in this session; the tool also accepts arbitrarily larger
  `--sizes` values (e.g. `100000`) for future runs, they just were not exercised here.
- **Search latency / embedding cache / update-to-queryable**: a separate synthetic vault of
  **1,000 notes**, indexed once with real Ollama embeddings, then reused for 80 queries across
  keyword/semantic/hybrid modes. Kept smaller than the indexing-only sizes above because this
  path makes real Ollama HTTP calls (the indexing-only benchmark does not attach an embedding
  service, so it can go much larger for the same time budget).
- **Retrieval quality**: the existing golden-set fixture,
  [`src/Kioku.Mcp.Server.Tests/Fixtures/EvalVault`](../src/Kioku.Mcp.Server.Tests/Fixtures/EvalVault)
  (27 notes) against
  [`golden-set.json`](../src/Kioku.Mcp.Server.Tests/Fixtures/golden-set.json)
  (22 scored queries + 2 no-answer probes) — unchanged from what
  [`docs/retrieval-eval.md`](retrieval-eval.md) documents.

## Reproduce

```bash
dotnet build src/Kioku.Mcp.Server/Kioku.Mcp.Server.csproj --configuration Release
dotnet run --project scripts/Kioku.Benchmarks -c Release -- suite \
  --sizes 100,500,1000,2000,10000,50000 \
  --search-vault-size 1000 --search-queries 80 --cold-start-runs 5 \
  --label baseline-2026-07
```

Run `dotnet run --project scripts/Kioku.Benchmarks -- suite --help` for the full option list
(you can point `--sizes` at larger values, change the search vault size/query count, or target a
different eval vault/golden set). Semantic and hybrid measurements require a reachable Ollama
with the configured embedding model pulled; everything else (cold start, indexing/memory,
keyword search, schema cost) works without it.

## 1. Cold-start time

Wall clock from spawning `dotnet Kioku.Mcp.Server.dll` over stdio to a completed MCP
`initialize` handshake, against a minimal one-note vault (so this isolates server startup cost
from indexing a real vault — see §2 for indexing time separately). 5 runs.

| | ms |
|---|---:|
| Mean | 674.6 |
| Median (p50) | 670.2 |
| Min | 661.0 |
| Max | 704.4 |
| First `tools/list` round-trip (mean, after initialize) | 57.2 |

## 2. Indexing time and memory by vault size

`VaultIndexService.InitializeAsync()` timed in-process (no embedding service attached — keyword
and metadata indexing only; embedding runs in the background in production and is measured
separately in §6). Memory is reported two ways: managed-heap delta
(`GC.GetTotalMemory(forceFullCollection: true)` before/after) and process working-set delta
(`Process.WorkingSet64` before/after) — these measure different things and can diverge (working
set includes the runtime, JIT, and everything else in the process, not just the index).

| Notes | Index time (ms) | Managed heap Δ | Working set Δ |
|---:|---:|---:|---:|
| 100 | 143.9 | 3.4 MB | 10.3 MB |
| 500 | 96.3 | 6.1 MB | 12.7 MB |
| 1,000 | 180.4 | 9.3 MB | 18.7 MB |
| 2,000 | 308.0 | 15.8 MB | 19.1 MB |
| 10,000 | 1,675.1 | 156.4 MB | 165.0 MB |
| 50,000 | 6,190.6 | 725.2 MB | 733.1 MB |

The 500-note run finishing faster than the 100-note run is JIT/warmup noise from being the first
`InitializeAsync()` call in the process, not a real regression — indexing time scales roughly
linearly with note count from 1,000 notes up (~0.13 ms/note), consistent with a single in-memory
inverted-index build with no I/O bottleneck at these sizes.

## 3. Search latency (p50/p95) by mode

80 queries synthesized from the 1,000-note search-scenario vault's own topic/tag pools (so every
query matches a meaningful, non-degenerate subset of notes), run once per mode. Semantic and
hybrid latency include the query-embedding HTTP round-trip to Ollama, matching what a real
`search_notes` call actually pays end-to-end — not just the in-memory ranking step.

| Mode | Samples | Mean (ms) | p50 (ms) | p95 (ms) | Min (ms) | Max (ms) |
|---|---:|---:|---:|---:|---:|---:|
| keyword | 80 | 1.8 | 1.4 | 2.3 | 0.4 | 25.1 |
| semantic | 80 | 31.5 | 29.8 | 46.1 | 27.0 | 56.9 |
| hybrid | 80 | 33.2 | 32.1 | 40.3 | 28.5 | 59.1 |

Keyword search is essentially free (sub-2ms typical) at this vault size; semantic/hybrid latency
is dominated by the Ollama embedding call for the query itself, not by the in-memory cosine
search over 1,000 vectors.

## 4. Update-to-queryable latency

A new note was written into the already-indexed, already-watched 1,000-note vault; the in-process
`VaultIndexService.Search()` path was polled every 50ms for a unique marker until it appeared.

| | |
|---|---|
| Elapsed | 509.3 ms |
| Found within timeout | yes (15s timeout) |

This is dominated by `VaultIndexService`'s 500ms `FileSystemWatcher` debounce window (by design,
to coalesce rapid successive writes/saves from an editor into one reindex), not by the reindex
work itself.

## 5. Embedding cache size and reuse

Same 1,000-note vault: indexed and embedded once (first pass), then re-initialized from scratch
against the *same, unchanged* vault a second time (second pass) to demonstrate cache reuse. The
clearest signal that the cache is doing its job is the second pass's dramatic speedup, not an
instrumented Ollama call count (more invasive, not necessary here).

| | First pass | Second pass |
|---|---:|---:|
| Index time | 153.5 ms | 158.9 ms |
| Embedding-backlog wait | 26,046.9 ms | 0.01 ms |
| Total | 26,200.4 ms | 158.9 ms |
| Notes embedded | 1,000 | 0 (cache hit — all 1,000 unchanged) |

**Speedup: 164.9x.** Cache file: `{vault}/.kioku/embeddings.bin` = 4,161,424 bytes (≈ 4.0 MB) for
1,000 notes (≈ 4.1 KB/note at 768-dim float32 vectors, before any per-note chunking overhead from
longer notes).

## 6. Schema-token cost by capability profile

Full `tools/list` JSON (name, description, input schema, output schema, behavioral annotations)
captured by spawning the real server per profile — `default` (the always-on tool groups) and
`all-capabilities` (every group from `docs/public-metadata.json` enabled) — via the
`ModelContextProtocol.Client` SDK, the same JSON-RPC exchange
[`scripts/generate-public-docs.mjs`](../scripts/generate-public-docs.mjs)'s
`inspectProfile`/`JsonLineMcpClient` already perform in Node, reimplemented in C# to keep this
tool in one language (see file header of
[`SchemaCostBenchmark.cs`](../scripts/Kioku.Benchmarks/Suite/SchemaCostBenchmark.cs)).

**Token counts below are an approximation** — `ceil(utf8Bytes / 4)`, a rough character-count
proxy for GPT-style tokenization. This repo has no tokenizer library dependency, so treat this as
an order-of-magnitude estimate for comparing profiles against each other, not an exact
provider-specific token cost.

| Profile | Tools | Schema JSON | Estimated tokens |
|---|---:|---:|---:|
| default | 43 | 53,313 bytes | ~13,329 |
| all-capabilities | 59 | 64,753 bytes | ~16,189 |
| **Delta** | **+16** | **+11,440 bytes** | **+2,860 (~21%)** |

## 7. Retrieval quality — Recall@K / MRR / NDCG@K

Computed by shelling out to the existing
[`scripts/Kioku.Eval`](../scripts/Kioku.Eval) runner (same `RetrievalMetrics` +
`GoldenSet` code `docs/retrieval-eval.md` documents as authoritative — this benchmark suite
does not reimplement the metric formulas, only parses `Kioku.Eval`'s Markdown table output into
the combined JSON report) against the 27-note `EvalVault` fixture and its 24-query golden set.
See [`docs/retrieval-eval.md`](retrieval-eval.md) for the full methodology, golden-set format,
and historical baseline comparisons (BM25 vs. naive TF, chunking before/after, etc.). Keyword and
semantic-mode numbers below reproduce exactly, run after run, against this fixed golden set;
hybrid-mode numbers do not — see the reproducibility note under the hybrid table below.

### keyword

| k | Precision@k | Recall@k | MRR | NDCG@k |
|---|---:|---:|---:|---:|
| 5 | 0.245 | 0.652 | 0.788 | 0.741 |
| 10 | 0.127 | 0.667 | 0.788 | 0.750 |

### semantic

| k | Precision@k | Recall@k | MRR | NDCG@k |
|---|---:|---:|---:|---:|
| 5 | 0.327 | 0.871 | 1.000 | 0.930 |
| 10 | 0.191 | 0.985 | 1.000 | 0.954 |

### hybrid

| k | Precision@k | Recall@k | MRR | NDCG@k |
|---|---:|---:|---:|---:|
| 5 | 0.273 | 0.727 | 0.876 | 0.824 |
| 10 | 0.173 | 0.902 | 0.876 | 0.867 |

**Reproducibility note.** Keyword and semantic-mode metrics above are exactly reproducible:
re-running `Kioku.Eval` against the same golden set reproduces byte-identical numbers every time.
Hybrid-mode metrics are **not** — four consecutive re-runs of
`dotnet run --project scripts/Kioku.Eval -- --modes hybrid --k 5` each produced slightly
different Recall@5/MRR/NDCG@5 figures, while keyword and semantic modes stayed identical across
those same re-runs. This is plausibly per-query embedding floating-point noise (repeated calls to
Ollama's `nomic-embed-text` can return marginally different vectors) propagating through
`HybridSearchService`'s Reciprocal Rank Fusion (RRF) tie-breaking, which is sensitive to small
score deltas between closely-ranked documents. The hybrid table above reflects one representative
run — consistent with the recorded baseline in `docs/retrieval-eval.md` in general magnitude and
ranking, but not a byte-for-byte reproduction of it. This is a pre-existing property of hybrid
mode, not something this benchmark suite introduced or fixes; see "Limitations, plainly" below.

Reproduce directly (bypassing the combined suite):

```bash
dotnet run --project scripts/Kioku.Eval -- --label baseline-2026-07
```

## Limitations, plainly

- **Single machine, single session.** No repeated trials across hardware, no statistical
  confidence intervals beyond the min/max/p50/p95 spread already reported per metric — read this
  as "the current implementation is roughly this fast on one 2026-era laptop-class CPU," not a
  cross-environment guarantee.
- **Synthetic vault content is not real notes.** Generated notes vary length/tags/links but
  follow one generator's statistical shape; real vaults have more structural variety (deeply
  nested folders, very long notes, heavy cross-linking, non-English content, malformed
  frontmatter) that could shift indexing/search timing in either direction.
- **Indexing (§2) and search/embedding (§3-5) used different vault sizes** (up to 50,000 vs.
  1,000 notes) because only the latter makes real Ollama HTTP calls; the 50,000-note figure in §2
  says nothing about semantic search latency at that scale — extrapolate cautiously, don't assume
  linear.
- **Token estimate (§6) is a character-count approximation**, not a real tokenizer count — see
  the caveat inline in that section.
- **Cold start (§1) points at a real, reachable Ollama** (`http://localhost:11434`); a
  deployment with Ollama unreachable would see the ping-timeout path instead (this degrades
  gracefully — keyword search still works — but changes the exact cold-start number).
- **Hybrid-mode retrieval metrics (§7) are not exactly reproducible run-to-run.** Keyword and
  semantic-mode Recall@K/MRR/NDCG@K reproduce identically every time against the fixed golden
  set; hybrid-mode numbers vary slightly between runs, plausibly from per-query embedding
  floating-point noise propagating through `HybridSearchService`'s RRF tie-breaking sensitivity
  to small score deltas. This is a pre-existing property of hybrid mode itself, not something
  introduced by (or fixed by) this benchmark suite — see the reproducibility note in §7.
